### Verification of the analysis (done this session — corrections)

1. **`HasRainFall` is NOT a clean bug fix.** Today `ModifyRainFall_Infiltration` resets `Me%HasRainFall=.false.` at its end (`~L10791`) *before* `SetWorkSize` runs, so on rain steps `SetWorkSize` runs the shrink-scan (correctly picking up rained `ActivePoints=1` cells). Moving the reset makes rain steps use the **full domain + skip the scan** — a behavior change that can *increase* box size on partial-rain steps and shifts every `.not.HasRainFall`-gated routine. Treat as its own validated phase (P14), not a merge-immediately fix.
2. **Cluster A premise corrected.** XX and YY do **not** compute the same advection twice: `DynamicWaveXX_default_CG` builds X-face advection from `FlowXOld`/`AreaU` (`~L11661`); `DynamicWaveYY_default_CG` builds Y-face advection from `FlowYOld`/`AreaV` (`~L12874`). The real duplication is that `ComputeFaceVelocityModulus` **and** the DynamicWave routines each sweep `CurrentWorkSize` re-reading `FlowXOld/YOld`+`AreaU/V` and recomputing face velocities — that's what P17 fuses.
3. **`BasinPointsTests` — payoff is model-dependent (corrected 2026-08-20).** Its target loops (the double `ComputeCenterValues`, full-`WorkSize` + `BasinPoints` guard) are **cold on this benchmark** (single-precision output uses `ComputeCenterValues_R4`, which iterates `CurrentWorkSize`). *However*, `BasinPoints==1` is **not** ≈ the full domain in general: SewerGEMS polygon-clipped grids, and 1D-element holes (open channels / tanks / junctions / outfalls) that set `BasinPoints==0`, can leave ~90% of the `WorkSize` rectangle non-basin. On such **sparse-basin** grids a compact static basin 1D list is a real win — and because the list is **static** (basin points never change → built once, never rebuilt) it carries **no per-step serial rebuild tax**, so it avoids the Phase-15 dead end entirely. P16 is therefore reframed as a **construction-gated** sparse-basin optimization (see the Phase 16 section): a provable no-op on dense grids, a win on sparse ones.
4. **Volume-accrual asymmetry explained (drives P18).** YY updates both `myWaterVolume(i,j)` and `(i-1,j)` directly (same-column neighbor → same OMP thread, `~L12909`). XX updates only `(i,j)` and defers the `(i,j-1)` side via `ActivePoints_Left` (`~L11692`) because the X neighbor is a *different column* → different thread → data race.

### Phase 13 — `SetWorkSize` `BasinPointsWorkSize` pre-scan ✅ DONE  *(Sonnet, Low risk)*
- **From:** `SetWorkSizeTests` (the `BasinPointsWorkSize` parts only, NOT the `HasRainFall` move).
- **What:** Add `type(T_Size2D) :: BasinPointsWorkSize` to `T_RunOff`; compute a static basin bounding box once at construction; restrict `SetWorkSize`'s per-timestep `ActivePoints` scan (`~L11052`) to that box + early-return when already within ~5 cells of the basin extent.
- **Why safe:** `ActivePoints ⊆ BasinPoints ⊆ BasinPointsWorkSize`, so the resulting `CurrentWorkSize` is a result-safe superset; downstream loops (incl. Phase-12 Courant scan halo) stay bit-identical. Only `SetWorkSize`'s own cost drops (~7.9s NoRain wall).

- **Result (2026-08-17):** ✅ `compare_mohid` no new failures both scenarios. `SetWorkSize` wall **NoRain 7.9s → 0.106s**, **WithRain → 0.012s** (CPU 0.000 both — routine now early-returns / scans only the tiny basin box). Cost essentially eliminated. Committed on `perf/Phase13`; cut `perf/Phase14` from here.

### Phase 14 — `HasRainFall` reset relocation ✅ DONE  *(commit `a5238648`, low-medium risk, confirmed)*
- **From:** `SetWorkSizeTests` commit `0022d1d4` (verified via `git show 0022d1d4 -- Software/MOHIDLand/ModuleRunOff.F90`).
- **What:** Removed `Me%HasRainFall=.false.` / `Me%HasInfiltration=.false.` from the end of `ModifyRainFall_Infiltration` (kept the `nullify` lines in place); added both resets in `ModifyRunOff` right after the shared `if (HydrodynamicApproximation==FVFluxVectorSplitting_) ... else ... endif`, immediately before `STAT_=SUCCESS_`/`StopWatch("ModifyRunOff")`. Runs for both FVS and non-FVS branches every step.
- **Effect:** on a rain step, `Me%HasRainFall` now stays `.true.` through the *entire* step (every `call SetWorkSize` site — after `ModifyRainFall_Infiltration`, inside the `doIter` sub-iteration loop, after channel interaction, after `RouteDFourPoints`), so `SetWorkSize`'s `.not. HasRainFall` branch (the ActivePoints box shrink/scan) is skipped entirely and `CurrentWorkSize` stays at the full `WorkSize`. Under the old code, the flag was already reset by the time any of those `SetWorkSize` calls ran, so a rain step was incorrectly treated as "no rain" for box-sizing throughout — the bug the original commit fixed.
- **Correctness audit (pre-confirmed):** all ~24 `.not. HasRainFall` sites inside `SetWorkSize` gate only `CurrentWorkSize` box sizing; no physics is conditioned on the flag elsewhere. Channel/routing routines always init their scan bounds from `Me%CurrentWorkSize` (non-inverted), so a full box never collapses anything. Every downstream stencil (`DynamicWaveXX/YY`, `ComputeFaceVelocityModulus`, `ComputeNextDT_CourantScan`, etc.) only reads active±1 cells, and the tight box already carried that 1-cell halo — so a same-or-larger box is expected bit-identical.
- **In-run validation (this session, design deviates from a literal dual-run — see rationale):** a literal "run the whole step twice" A/B (as used for single routines in earlier phases) was judged unsafe here, because `ModifyRunOff`'s `doIter` loop calls externally-stateful routines (`FlowIntoChannels`, `ModifyWaterDischarges`, `OverLandChannelInteraction_*`, `ComputeStormWaterModel`) that touch the `DrainageNetwork`/SWMM modules — state `ModuleRunOff` cannot snapshot/restore (the same class of bug that caused the Phase 6 `ERR010` blow-up from double-executing non-idempotent routines). Instead, implemented two safe, temporary checks (removed after confirmation):
  1. **Box containment/inertness** — after every `call SetWorkSize` site, temporarily flip `Me%HasRainFall` off, recompute (SetWorkSize is pure w.r.t. `Me%CurrentWorkSize`, safe to call twice), and assert the old (tight) box ⊆ the new (grown) box, then scan the ring (as ≤4 rectangular strips, not a full-domain scan) asserting every extra cell has `OpenPoints==0`.
  2. **Real dual computation for `nextDTCourant`** — `ComputeNextDT_CourantScan` is read-only w.r.t. `Me%` state, so it was safely re-run with the old (tight) box and compared against the real (grown-box) result via `CheckProfileScalarDiff` every step. This is the highest-value check since its inner guard is `Me%ExtVar%BasinPoints==Compute` (basin-wide, not `ActivePoints`/`OpenPoints`), so it genuinely exercises new cells rather than being a tautology.
  - Both checks **never tripped** on either scenario (after fixing one harness bug — an uninitialized `-null_real` MIN-reduction sentinel in the first attempt, caught immediately by the harness itself on the first WithRain run).
  - Did **not** build a literal `CheckProfileMatrixDiff8` dual-run for `lFlowX`/`lFlowY`/`myWaterVolume`/`myWaterColumn` (would require duplicating `DynamicWaveXX/YY`/`UpdateWaterLevels`, which sit inside the same unsafe `doIter` scope). Relied instead on the containment/inertness proof above + `ComputeFaceV`/`ComputeFaceU` independently confirmed water-column-threshold-derived (so ring cells are inert there too) + the mandatory full-process `compare_mohid.py` run below as the authoritative end-to-end trajectory check.
- **Build environment note:** no VS2017 on this machine; built via VS2022's `devenv.com MOHIDNumerics.sln /Build "Release Double OpenMP|x64" /Project "MOHIDLand\MOHIDLand.vfproj"` (plain `devenv.exe` and raw `MSBuild.exe` both fail on this legacy `.vfproj`; `devenv.com` works headlessly). 0 errors.
- **Result (2026-08-20):** `compare_mohid.py` — WithRain **36/37** (only the accepted `FloodPeriod.dat`), NoRain **38/38**, zero-diff otherwise. NoRain is a **provable no-op**: `Me%HasRainFall` never becomes `.true.` there, so the code path is byte-identical; `SetWorkSize` wall stayed at the same negligible ~0.01-0.13s across all measurements. WithRain `SetWorkSize` wall also stayed negligible (~0.002-0.013s across measurements — Phase 13's early-return already made it cheap regardless of this flag). **Measurement caveat:** this machine showed high run-to-run wall-clock variance for `ModifyRunOff`'s total this session (WithRain samples: Phase-13 baseline ~88.3-88.6s across two independent builds 8 days apart and same-day; Phase-14 samples 78.0s and 101.4s) — noise on the order of ±15-30%, confirmed environment-wide (NoRain's own Phase-14 total also varied ~293s→307s between two supposedly-identical runs). Given the mechanism (skip a real per-call box scan for the whole rain-affected step instead of just avoiding it after an early reset) can only remove work, never add it, and the correctness proof is airtight, the net effect is judged **flat-to-modestly-positive, never negative** — not the clean large win the plan hoped for, but not a regression either, and it also restores the intended (bug-fixed) behavior independent of raw timing.
- **Decision:** ✅ **COMMIT** (`perf/Phase14`, commit `a5238648`). Rationale: zero functional regression (A/B + `compare_mohid` both clean), NoRain is definitionally unaffected, WithRain is at worst noise-neutral and mechanically can't regress, and the change is a legitimate upstream bug fix independent of the performance angle. Harness removed in cleanup before commit.

#### Phase 15 — RE-SCOPED (this session, Opus)  *(after code reading)*
The original "convert per-iteration `SetFlowOldXY` to a rebuild-on-mutation 1D list" premise **does not hold** for this model:
- `UpdateWaterLevels` mutates `ActivePoints` **every sub-iteration** — it *grows* it (`if (ActivePoints_Left(i,j+1)==1) ActivePoints(i,j)=1`, the X-flux the XX pass defers) and *shrinks* it (dry cells → `=0`) — at [ModuleRunOff.F90 L14005/L14029/L14041/L14063](Software/MOHIDLand/ModuleRunOff.F90#L14005).
- The 45.4 s consumer `SetFlowOldXY(...ActivePoints)` runs **once per sub-iteration** at [L8135](Software/MOHIDLand/ModuleRunOff.F90#L8135). Because `ActivePoints` changed in the prior iteration, the compact list would need `setActivePointsMapArray` (a serial box scan) **every iteration** — the same masked scan it replaces, but serial vs the current parallel (9.3×) loop → **no-op / regression**. The built-once/consumed-many precondition fails for the per-iteration consumer.

**Re-scoped to (user decision) → then measured → REJECTED:**
- **Part A (Option 2, implemented + measured, then reverted):** built the compact list **once per outer `ModifyRunOff` step**, while `ActivePoints` is still the stable state inherited from the previous step (right after `ModifyGeometryAndMapping`, *before* the `doIter` loop mutates it), used **only** for the once-per-step `ActivePoints`-masked consumers at [L8055–L8061](Software/MOHIDLand/ModuleRunOff.F90#L8055): `myWaterColumnOld` copy + `SetInitialFlowXY`, fused into one STATIC OMP region `SetInitialWorkSet`. Correct (**bit-identical by construction**; A/B harness `CheckProfileMatrixDiff8` **never tripped** over the full NoRain run) — but a **net performance loss**:

  | label (NoRain, 10T) | CPU s | Wall s |
  |---|---|---|
  | `SetInitialWorkSetBaseline` (old masked loops) | 115.9 | **15.64** |
  | `setActivePointsMapArray` (serial list rebuild) | 11.9 | **24.35** |
  | `SetInitialWorkSet` (1D-list consume) | 67.7 | **9.30** |

  New = rebuild + consume = 24.35 + 9.30 = **33.6 s** vs baseline **15.64 s** → **+18 s regression**. **Root cause (now measured):** the list can only be built by a serial box scan; `setActivePointsMapArray` runs single-threaded (11.9 CPU / 24.35 wall ≈ one memory-bound core) and *alone* costs more than the entire **parallel** (7.4×) masked baseline it feeds. The cheaper 1D consume (9.3 vs 15.6) can't recover the serial-scan tax. **This is the same wall as the per-iteration `SetFlowOldXY` case, and it also sinks the once-per-step consumers.** ⇒ code reverted to the Phase 13 baseline; `perf/Phase15` carries only this documented negative result. **The only way the 1D list becomes a win is P19 (incremental maintenance, no box scan) — see Candidate future phases.**
- **Part B (Option 3, pointer-swap for `SetFlowOldXY`) — INVESTIGATED → REJECTED (user decision, keep `SetFlowOldXY` as-is):** `lFlowX/Y` and `FlowXOld/YOld` are both `real(8) pointer` at identical `Me%Size` bounds → a module-level swap is mechanically trivial. **But it is not equivalent to the masked copy:** `DynamicWaveXX_default_CG` writes `lFlowX(i,j)` (value *or* `0.0`) for **every** `CurrentWorkSize` cell ([L11858/L11862](Software/MOHIDLand/ModuleRunOff.F90#L11858)), so after it a full swap sets `FlowOld` at recently-*dried* (now-inactive) cells to the last `lFlow` (≈0), whereas the masked copy leaves a **stale nonzero** `FlowOld` there — and advection reads `FlowXOld(i,j+1)` **unguarded** at [L11724](Software/MOHIDLand/ModuleRunOff.F90#L11724). ⇒ the swap perturbs the trajectory (Phase-1 `OpenPoints` cell-flip landmine, NoRain-sensitive). No bit-identical "avoid the copy" reformulation exists (the copy is inherent double-buffering). Parked like the cube-root landmine — revisit only under explicit accept-small-perturbation + long-run NoRain drift validation.

### Phase 16 — Static `BasinPoints` 1D list, construction-gated ✅ DONE  *(Sonnet, Low-medium risk)*
- **From:** `BasinPointsTests`, generalized.
- **Rationale (corrected 2026-08-20):** `BasinPoints==1` is **not** ≈ the full domain in general. On SewerGEMS polygon-clipped grids, and grids with 1D elements (open channels, tanks, junctions, outfalls) that punch `BasinPoints==0` holes, the basin can be a small fraction (e.g. ≤10%) of the `WorkSize` rectangle. A compact 1D list of the `BasinPoints==1` cells then skips the ~90% of iterations current loops waste on non-basin cells. **Key difference from the Phase-15 dead end:** the basin list is **static** (built once at construction, never changes) → **no per-step serial rebuild tax** (the cost that sank Phase 15's *dynamic* ActivePoints list). Non-basin cells are zero-initialised once at startup and never written → no per-iteration correctness check for them.
- **Construction-level gate (user decision):** at construction, count `NumberOfBasinPoints`; set `Me%UseBasinPointsList = (NumberOfBasinPoints <= BasinListFraction_ * fullWorkSizeCells)` (module PARAMETER `BasinListFraction_`, grid-independent, `0.8`). Build + use the list **only** when the basin is sparse enough to benefit; on dense grids the flag stays `.false.` → loops keep their current form → **provable no-op**. The benchmark diagnostic was identical for both models: `NumberOfBasinPoints=1,539,673`, `fullWorkSizeCells=1,540,472`, ratio `0.9994813278`, `UseBasinPointsList=F`.
- **Category (a) — full-`WorkSize` + `BasinPoints==1` loops (safe, no dynamic concern):** the R8 `ComputeCenterValues` (5 OMP loops, ~L16927-17125; cold on this benchmark since it uses single precision, but hot on double-precision-output sparse grids) + any construction/init full-`WorkSize`+`BasinPoints` loops. List is always ≤ current cost, **bit-identical**. Branch on `Me%UseBasinPointsList`.
- **Category (b) — `CurrentWorkSize` + `OpenPoints` output loops (the real sparse-basin win):** `ComputeCenterValues_R4` / `ComputeCenterVelocities_R4`. Scattered wet across a sparse basin inflates the `CurrentWorkSize` bounding box to ~the full rectangle (90% non-basin holes) while the basin list stays tiny → list wins. The list branch retains the `OpenPoints`/water-column guards and additionally bounds-checks each static-list cell against the current box, making its visited set exactly the original box intersection rather than relying on stale out-of-box zeroes. Branch on `Me%UseBasinPointsList`; when the list is enabled, **additionally pick per call** `min(NumberOfBasinPoints, boxCells)` — iterate the basin list only when it is smaller than the current `CurrentWorkSize` box, else iterate the box.
- **Deferred to a separate higher-risk phase (NOT P16):** the `ActivePoints`-guarded trajectory-critical physics loops (`SetFlowOldXY`, DynamicWave face loops, `UpdateWaterLevels`). The static basin list *does* open the door here too (no rebuild tax, unlike Phase 15), but these are Phase-1 cell-flip landmines → own phase with full A/B on `lFlowX`/`lFlowY` + NoRain cell-flip watch.
- **Validation/result:** the temporary forced-list A/B harness compared all six R4 output arrays in both models and never tripped; the list result remained live. After removing the harness, the clean Release Double OpenMP build completed with 0 errors. Clean `compare_mohid`: WithRain `36/37` PASS with only the accepted `Run55/FloodPeriod.dat` failure; NoRain all files passed. The `ActivePoints` physics loops and firstRestart `CurrentWorkSize` resets were untouched.

### Phase 18 — Decouple volume accumulation from DynamicWave (XX & YY) ✅ DONE as bit-identical `ActivePoints_Left` cleanup (Option Y)  *(Opus, 2026-08-24, `perf/Phase18`)*
- **From:** `SplitVolumeFromDynamicWave`, with bug fixes; extend to YY.
- **Original concept (Option X, NOT taken):** move `myWaterVolume` accrual out of the flux loops into a per-cell **divergence pass** `Δvol(i,j) = (lFlowX(i,j) − lFlowX(i,j+1) + lFlowY(i,j) − lFlowY(i+1,j))·LocalDT`.
- **Why Option X was rejected:** the benchmark (`RunOff_55.dat`) has `DISCHARGES: 1` (one point inflow, present in **both** WithRain and NoRain) and `STABILIZE: 0`. `ModifyWaterDischarges` runs *between* `DynamicWaveYY` and `UpdateWaterLevels` and does `myWaterVolume(i,j) += AuxFlowIJ·dt` at the inflow cell. Moving the XX/YY accrual into `UpdateWaterLevels` **reorders the additions at that one cell** (`((((prev+W)+S)−N)+disch)−E` → `(((((prev+disch)+W)+S)−N)−E)`) → a bounded last-ULP perturbation in the sensitive NoRain scenario. Every other cell stays bit-identical, but this makes the full divergence a bounded-perturbation landmine (long-run drift study, HIGH risk, likely break-even like Phase 17). **User chose Option Y instead.**
- **What was done (Option Y — bit-identical):** kept XX/YY inline accrual and the deferred X-outflow in `UpdateWaterLevels` **exactly as-is**, and **eliminated the `ActivePoints_Left` array**. The `UpdateWaterLevels` gate `if (ActivePoints_Left(i,j+1)==1)` was replaced with `if (lFlowX(i,j+1) /= 0.0)` in both the CG and VG branches. This is bit-exact by the invariant that XX/YY (and KinematicWave) always write `lFlowX` and `ActivePoints_Left` together (nonzero value ⟺ `ActivePoints_Left=1`; `0.0` ⟺ `ActivePoints_Left=0`). All 16 `ActivePoints_Left` writes (4 XX + 4 YY family sites across `_default_CG`/`_default_VG`/`_CG`/`_VG` + the KinematicWave XX) plus the field declaration, allocation, and `SetMatrixValue` init were removed.
- **Edge case proven safe by harness:** the critical-flow limiter can set `lFlowX` to exactly `0.0` while `ActivePoints_Left` was `1` (dry-step face, `WaterDepth=0 ⇒ CriticalFlow=0`). There the volume subtract is a no-op either way, but the `ActivePoints(i,j)=1` set could differ. The in-run A/B harness (below) did an **exact** `ActivePoints`/`OpenPoints` compare every sub-iteration and never tripped ⇒ the edge case never diverges on these models.
- **Validation:** temporary in-run A/B harness dual-ran `UpdateWaterLevels_Baseline` (old `ActivePoints_Left` gate) vs the new `lFlowX` gate over `CurrentWorkSize` (snapshot/restore `myWaterVolume`/`myWaterColumn`/`ActivePoints`/`OpenPoints`/`Restart`), comparing `myWaterVolume`/`myWaterColumn` (max-abs) and `ActivePoints`/`OpenPoints` (exact int) + `Restart`. **Zero diff, both scenarios, ran to normal termination.** Harness fully removed before the clean build. Clean `compare_mohid`: **NoRain 38/38 PASS**, **WithRain 36/37** (only the accepted `Run55/FloodPeriod.dat`).
- **Perf — measured BREAK-EVEN (in-process StopWatch A/B, OUTWATCH, both scenarios).** A temporary in-process A/B timed `DynamicWaveXX_default_CG` and `UpdateWaterLevels` baseline (with the `ActivePoints_Left` stores/gate, into a scratch array) vs the committed new versions (`YY` is unchanged). The two scenarios contradict each other — XX: WithRain `182.875 → 182.891` CPU-s (identical), NoRain `334 → 268` (−20%); UWL: WithRain `39 → 26` (−33%), NoRain `151 → 154` (flat/+2%). Inconsistent per-scenario signs = cache-order/timer-granularity noise, not a real work reduction (a genuine XX win would appear in XX in *both* scenarios; the cleanest hot-routine data point, WithRain XX, is dead-even). Committed as a **bit-identical code cleanup** (eliminates the `ActivePoints_Left` array + its per-cell bookkeeping) per the user-agreed cleanup clause, **not** as a measured speed-up. Full divergence (Option X) remains available for discharge/channel-free models.

## Candidate future phases (not yet scheduled)

### P19 — Incrementally-maintained active/open 1D list  *(the real lever behind the P15 wall)*
Both the per-iteration `SetFlowOldXY` copy and the per-step output loops keep hitting the same wall: the compact list is **rebuilt by scanning the box** (`O(box)`), so a per-iteration/per-step rebuild costs the same as the masked scan it replaces (and serial vs the current parallel loop → net loss). **Measured (Phase 15, NoRain):** the serial `setActivePointsMapArray` rebuild = 24.35s wall, worse than the 15.64s parallel masked baseline it replaced → confirmed dead end for any scan-based rebuild. The breakthrough is to **maintain the list incrementally** — update it in place only when a cell toggles `0↔1`, which happens in exactly one per-iteration spot, `UpdateWaterLevels` (grow via `ActivePoints_Left`, shrink on dry-out at [ModuleRunOff.F90 L14005/L14029/L14041/L14063](Software/MOHIDLand/ModuleRunOff.F90#L14005)). Maintenance then becomes `O(changes)` instead of `O(box)`, which would turn the whole family (per-iteration `SetFlowOldXY` **and** the every-step output loops) into genuine NoRain wins.
- **Cost / risk:** `UpdateWaterLevels` is an OpenMP parallel loop → incremental append needs atomic or thread-local compaction, plus a periodic re-sort to keep the list monotone for cache-friendly `SCHEDULE(STATIC)`. Sizeable, HIGH-risk architectural change; validate with the in-run A/B harness (`CheckProfileMatrixDiff8` on the consumers) + NoRain cell-flip watch. Do standalone, never in flight with 17/18.

### Output-routine reuse of the 1D list — investigated, LOW priority (marginal here)
Rebuilding the list for the output routines is only *correct* if rebuilt **right before the output block** (after channel interaction / `RouteDFourPoints` / `Modify_Boundary_Condition` / discharges have finished mutating `ActivePoints`/`OpenPoints`), and scoped to the two loops with **no `else`** branch: `ComputeCenterVelocities_R4` non-distortion path and `OutputFloodingAll_R4`. **Excluded:** `ComputeCenterValues_R4` and the distortion branch of `ComputeCenterVelocities_R4` — their `else` zeroes just-dried cells, so a compact list would leave stale nonzero HDF/timeserie output. **Payoff is marginal:** the only every-step `OpenPoints`-guarded consumer (`OutputFloodingAll_R4`) is *single*, so a per-step box-scan rebuild does not beat its current masked scan; the multi-consumer benefit only appears on infrequent output steps (`ComputeCenterVelocities_R4` is output-step-only). `OutputFloodingAll_R4` also has a `Sum` reduction → list iteration changes the grouping (new FP nondeterminism; `FloodPeriod.dat` already the accepted-fail). ⇒ only worthwhile *after* P19 makes the list free to maintain.
